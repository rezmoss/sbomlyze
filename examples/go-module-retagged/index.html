Go module re-tagged after release

The same go-containerregistry v0.20.4, two different checksums: the maintainer moved the tag after Go's checksum database had recorded it.

gosource Integrity driftdeny_integrity_drift policyDigest coverageSARIF

What happened

In May 2025 the v0.20.4 tag of github.com/google/go-containerregistry was deleted and created again on a different commit (upstream issue #2107). proxy.golang.org and sum.golang.org had already recorded the first one.

By default Go downloads through proxy.golang.org, which still serves the first v0.20.4, so nothing looks wrong. Fetching the moved tag directly from GitHub with checksum checking on fails with SECURITY ERROR ... checksum mismatch. With GOPRIVATE covering the module path, a common setting in companies with private repositories, Go fetches directly, skips the checksum database, and takes the moved tag without a warning.

This example resolves the dependencies of the same one-line program both ways (go mod tidy). The two go.sum files record different hashes for the same version, and sbomlyze reports it as integrity drift. With deny_integrity_drift the build fails.

What actually changed between the two v0.20.4 contents is one file, .github/workflows/release.yml (see the content diff below). Harmless here; the point is that nothing else in the build would have said so. Two more re-tags of this kind, also reported upstream: MSAL for Go v1.10.0 (#681) and go-swagger v0.31.0 (#3118).

The second diff is the control: syft 1.55.0 → 1.57.0, where all 262 Go modules that kept their version could be checksum-compared and none drifted.

What this does not prove. The SBOMs record go.sum checksums, not compiled code. Syft's SPDX output does not carry Go h1 checksums, so this check needs Syft JSON or CycloneDX.
